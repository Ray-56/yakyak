# ADR-0002：协议状态、I/O 动作与时间分离

状态：Accepted（2026-10-20，用户确认本会话完整设计草稿）。关联：AC-00-04。

本记录确认设计选择，不代表通信内核已实现或 AC-00-04 已通过整项验收。

## 问题

协议处理同时涉及判断规则、网络收发、定时器和资源回收。如果这些职责混在一起，就难以独立检查规则，也难以解释超时、取消和失败时的行为。

## 设计决定

### 1. 状态机负责决定，执行器负责操作

状态机接收消息、定时器到期、明确命令和执行结果等事件，结合当前状态与外部提供的单调时间，更新状态并输出动作。

执行器负责实际收发网络消息、设置和取消定时器，并将结果作为事件返回。状态机不直接操作网络，也不自行等待时间流逝。

同一个协议对象逐一处理事件；测试可以明确安排事件顺序。

### 2. 两种时间分别使用

协议超时与重传间隔使用单调时钟（monotonic clock）；日志和报告中的日期、时刻使用墙上时间（wall-clock time）。

测试提供可手动推进的时间，不依赖长时间 `sleep`。

### 3. 定时器通知必须检查有效性

每次设置或重新设置定时器，都使用能区分本次提醒的标识。到期事件携带该标识。

状态机只处理标识有效、且确实到期的通知。取消、重设或处理到期事件后，旧标识失效；随后到达的旧通知被忽略。

### 4. 动作及结果必须对应原来的那次工作

执行器返回需要关注的成功或失败结果，不自行决定协议重试。本地发送成功不能证明对方已经收到或处理消息。

消息内容在发送完成前必须保持有效。排队动作执行前应检查是否仍被允许；迟到结果不能影响已经结束的对象，或后来复用标识的新对象。已经交给网络的数据无法通过本地取消撤回。

### 5. 停止请求必须落实为实际退出

任务有明确所有者，由所有者请求停止，并等待任务结束，也就是 `join`。

停止通知必须能唤醒无流量时的等待任务。完成必要清理、确认退出结果后，才能报告停止完成。

业务结束、协议记录保留和执行资源释放分别判断。仍有协议收尾义务时，应保留必要记录和执行能力；共享资源由其所有者管理。

队列、定时器和保留记录需要有界，具体上限在对应实现任务中明确。超限必须显式处理，不能静默丢失关键事件。

## 一次超时的过程

1. 状态机开始等待，输出设置定时器动作。
2. 执行器登记定时器。
3. 截止时间到达，执行器送回到期事件。
4. 状态机检查事件有效性和当前状态，按协议规则输出重传及后续计时动作。
5. 执行器实际发包，返回对应执行结果。
6. 收到响应或结束命令后，状态机调整状态、使不再需要的提醒失效，并要求执行必要清理。

## 测试设计

后续实现时，应检查：

| 场景 | 预期 |
|---|---|
| 截止时间前后 | 到期前不触发，到期后按规则产生动作 |
| 响应与超时交错 | 两种处理顺序均有明确结果 |
| 取消或重设后旧通知到达 | 旧通知不再触发动作 |
| 墙上时间调整 | 不改变协议超时判断 |
| 执行失败、结果迟到 | 返回对应结果，不影响其他轮次 |
| 无流量时停止 | 能唤醒、退出、完成必要清理 |
| 单项业务结束 | 不误关其他业务使用的共享资源 |
| 实际网络发送 | 独立接收端观察到预期消息 |

状态机测试检查判断和动作；网络测试检查真实 I/O；回收测试检查任务与资源的实际状态。本表是测试设计，尚未实现或执行这些场景。

## 选择理由与代价

这种分工让协议规则可以独立测试，使外部操作和清理各有明确职责。

把所有工作混在一起，起步较直观，但测试容易依赖真实网络和等待，故障也较难定位。

当前方案需要明确传递事件、动作和结果，并处理迟到事件。职责分离不要求立即拆成多个 crate、线程或进程。

## 何时重审

后续实现若发现事件顺序、错误处理、资源上限或回收方式不能满足对应验收要求，应记录原因并重新评审。

具体 Rust 类型、运行时和定时器实现，在对应任务中选择。
