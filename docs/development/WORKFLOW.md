# 每日开发工作流

## 只开一个进行中的目标

CURRENT指向一张任务卡，任务卡引用一个AC或其明确子集。阅读只需当前章节、相关RFC段落与ADR，不必一次读完27章。允许为了理解后续章节阅读资料，但不因此扩展当前实现范围。

## 从开始到结束

| 步骤 | 输出 | 停止条件 |
|---|---|---|
| 读目标与依赖 | 知道输入、输出、边界 | 前置未通过先完成前置 |
| 写任务卡 | 本次做/不做、测试计划 | 不清楚可观察结果就先澄清模型 |
| 写最小失败测试 | 断言能因缺失行为失败 | 环境错误不算TDD红灯 |
| 本人实现 | 小块可解释的Rust代码 | 不顺手扩展其他AC |
| 目标+回归 | 真实命令和数量 | 0测试、跳过、未运行不通过 |
| 独立验证 | 针对网络/媒体的外部证据 | 自己调用自己不足以证明互通 |
| 写验收报告 | commit、环境、结果、证据 | 缺证据先ready_for_review或blocked |
| 人工确认 | passed、CURRENT下一目标 | Codex不自动推进下一章 |

## 分支与提交

初始化在独立重写分支；后续可用`feat/ch01-ac01-02-byte-boundaries`。一个变更集不要混进整个章节。提交分离测试、实现与验收报告，保留可审阅性；不规定每个微小函数都必须一个PR。

实现和测试提交C → 在干净C上运行 → 文档提交D记录tested_commit=C。改变被测代码要重跑。合并方式若改了哈希，在最终commit重验或保留可达的验证引用。

## 与Codex协作

讲解请求：“解释AC-01-02的字节边界和失败用例，不要实现核心代码。”
评审请求：“只review当前diff，对照AC-01-02，按严重度指出协议/边界/测试盲点，不直接修改。”
用例请求：“只补测试设计/独立fixture建议，不写生产解析器；说明哪些案例仍待我实现。”

若以后明确让Codex写某一段，需在该次任务说明授权文件与范围，不把初始化授权沿用到整个路线图。

## 状态维护

只修改progress.json并重新生成视图。ready_for_review/passed都需要真实实现commit和现有验收报告；passed还需要用户确认记录。blocked必须写具体原因和解除条件。暂停开发时更新CURRENT中的已做/未做/下一步，避免把未提交草稿误记为通过。
